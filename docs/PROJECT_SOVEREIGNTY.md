# Project Sovereignty Contract

This project must preserve its core product meaning, provenance, artifact lifecycle, and critical operating capability if an external provider, API, SDK, model, connector, runtime, sibling project, or vendor disappears or materially changes.

## Invariants

- **Human authority comes first.** Authorized humans are the root of consequential authority. Models, agents, providers, workflows, evidence, learned knowledge, fingerprints, proof cookies, and automations may inform or constrain a proposal but may not manufacture, renew, widen, or replay authority.
- Human authority does not rewrite reality. Approval can authorize an action; only evidence can support a truthful execution or outcome claim.
- Project-owned contracts define canonical inputs, outputs, errors, authority, state, evidence, provenance, canon, and completion semantics.
- External providers and sibling projects are adapters/capabilities, not project identity.
- Critical dependencies are classified `REPLACEABLE`, `DEGRADED_FALLBACK`, `HARD_DEPENDENCY`, or `UNKNOWN`.
- Critical capability must keep an alternate adapter, local/open implementation, deterministic fallback, export/manual recovery path, or honest safe degraded mode unless a documented hard dependency is explicitly accepted.
- Critical data and story meaning keep project-owned semantics and a migration/export path; vendor IDs are provenance, not canonical identity.
- Provider swaps must not broaden authority, replay stale approvals, duplicate mutations, weaken tenant isolation, or weaken evidence requirements.
- Provider-specific results map into project-owned receipts; provider acceptance is not publication, promotion, or human-outcome proof.
- When operated through Founder Control Room, StoryEngine remains a sovereign subsystem, not a separate founder operating system.

## World as experience and knowledge

Legitimate real-world interaction may become evidence-bearing experience: author/user reports, runtime behavior, provider responses, editing outcomes, publication outcomes, experiments, analytics, documents, repository history, operational failures, and verified results.

```text
World → observation → provenance → evidence classification → experience receipt → knowledge candidate → contradiction / red-team check → context + confidence + freshness → working knowledge → proposal → authorized action when applicable → outcome evidence → new experience
```

Experience is not automatically truth. One observation is not automatically a rule. Working knowledge must remain challengeable, provenance-backed, scoped, freshness-aware, and supersedable.

## StoryEngine-specific boundary

World-derived learning must not silently alter authorship, canon, artifact ownership, tenant boundaries, privacy, publication authority, or promotion state. Learned patterns may inform proposals; they do not become editorial, publication, or cross-tenant authority.

## Mandatory audit questions

> If every named provider or sibling project disappeared now, what stops, what survives, what is the recovery path, and what evidence proves the answer?

> What experience is this system learning from, what is its provenance, what would falsify the current conclusion, and who actually holds authority for the next consequential action?

Architecture docs are not failover or learning proof. Verify contract, adapter, focused test, runtime, provenance, data-exit path, authority, and real-path evidence separately.

Future provider or knowledge-system work must follow: Reality → ULTRATHINK → Red Team 1 → Lindy → L99 → OODA → smallest reversible implementation → focused proof → Red Team 2 / provider-loss + knowledge-corruption attack → Documentation Truth → rollback → next gate.
